# Context-Free Grammar for SQL Injection Detection

## 1. Introduction

A Context-Free Grammar (CFG) is a set of production rules used to describe the structure of a language.

In this project, CFG is used to describe SQL SELECT queries and identify suspicious structures associated with SQL injection attacks.

## 2. Grammar Rules

These rules are exactly what the parser in `sqli/parser.py` implements.
Words in `UPPERCASE` and quoted symbols are terminals (tokens). `|` means "or", `( )*` means "zero or more", `[ ]` means "optional".

```text
query        -> select_stmt ( UNION [ALL] select_stmt )* [ ";" ]
select_stmt  -> SELECT select_list FROM table
                [ WHERE condition ]
                [ ORDER BY column [ ASC | DESC ] ]
                [ LIMIT NUMBER ]
select_list  -> "*" | column ( "," column )*

condition    -> and_expr ( OR and_expr )*
and_expr     -> not_expr ( AND not_expr )*
not_expr     -> NOT not_expr | primary
primary      -> "(" condition ")" | comparison
comparison   -> operand operator operand
              | operand LIKE operand
              | operand IN "(" literal ( "," literal )* ")"
operand      -> column | literal
literal      -> NUMBER | STRING

operator     -> = | <> | != | < | > | <= | >=
table        -> identifier
column       -> identifier            (may be written table.column)
identifier   -> letter (letter | digit | _)*
```

Tokens (produced by the lexer in `sqli/lexer.py`): `KEYWORD`, `IDENT`, `NUMBER`,
`STRING` (single or double quotes, `''` inside a string is an escaped quote),
`OP`, `STAR`, `COMMA`, `LPAREN`, `RPAREN`, `SEMI`, `COMMENT` (`--`, `#`, `/* */`).

## 3. Ambiguity Discussion

SQL expressions containing both `AND` and `OR` can be interpreted differently if operator precedence is not defined clearly.

The "obvious" grammar

```text
condition -> condition OR condition | condition AND condition | comparison
```

is **ambiguous**. The condition `a=1 OR b=2 AND c=3` has two different parse trees:

```text
Tree A:  (a=1 OR b=2) AND c=3        Tree B:  a=1 OR (b=2 AND c=3)
```

A detector that reasons about tree structure needs exactly **one** tree per query, so we split the rule into layers.

In our grammar, `and_expr` groups expressions connected by `AND`, while `condition` combines these expressions using `OR`. Therefore, `AND` has higher precedence than `OR`.

The `not_expr` rule handles the `NOT` operator, and parentheses allow conditions to be grouped explicitly.

With these layers every supported query has one parse tree (checked by the test `test_precedence_and_binds_tighter` in `tests/test_scanner.py`).

## 4. Detection Rules

The SQL injection detector analyzes SQL queries using the grammar and detection techniques implemented in the project.

1. **Lexical Analysis:** Identifies SQL keywords, identifiers, operators, strings, and numbers.
2. **Syntax Validation:** Checks whether a query follows the supported grammar.
3. **Structural Analysis:** Examines the query structure for suspicious patterns.
4. **Detection Result:** Reports the result based on the checks implemented by the detector.

| Rule | What triggers it | Example |
|---|---|---|
| `LEXICAL` | Unterminated string or block comment | `id = '5` |
| `COMMENT` | `--`, `#` or `/* */` | `admin'--` |
| `PARSE_ERROR` | Query is not derivable from the grammar | `WHERE id = 1 OR` |
| `STACKED` | Another statement after `;` | `; DROP TABLE users` |
| `UNION` | A second SELECT branch in the tree | `UNION SELECT username, password ...` |
| `OR_BRANCH` | An `Or` node inside `WHERE` | `id = '' OR '1'='1'` |
| `AND_BRANCH` | An `And` node inside `WHERE` (only with `--strict`) | `id = 1 AND name = 'x'` |
| `TAUTOLOGY` | A constant comparison that is always true, or a column compared with itself | `1=1`, `'a'='a'` |
| `CONTRADICTION` | A constant comparison that is always false | `AND 1=2` |

A query that follows the grammar is not necessarily safe, and a syntax error alone does not prove an SQL injection attack. The detector's results depend on the rules and techniques implemented in the project.

## 6. Limitations

- The grammar covers a **subset** of SQL (single-table SELECT). Subqueries, functions such as `COUNT(*)`, table aliases and `BETWEEN` are not supported, so such queries are reported as `PARSE_ERROR`.
- A legitimate `OR` query (`WHERE a = 1 OR a = 2`) is flagged under the default policy. The `Policy` class in `sqli/detector.py` lets an application change what it expects.
- Encoded payloads (URL-encoding, hex) must be decoded before scanning.
- The real fix for SQL injection is parameterized queries (prepared statements), where the query structure cannot change at all.
